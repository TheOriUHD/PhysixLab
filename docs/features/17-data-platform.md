# 17 · Data, export, persistence, sharing, API, PWA (package DT)

Depends on: foundation (asset store, migrations), time (replays), visuals (thumbnails), maps/gallery (local gallery UI is MP-50 — DT provides the storage layer).

Honest scope: there is no backend. "Cloud saves/accounts" are provided as **folder sync via the File System Access API** (works with Dropbox/Google Drive/iCloud/OneDrive desktop folders) plus export/import; "multiplayer/collab" is **peer-to-peer WebRTC with copy/paste signalling and BroadcastChannel for same-device tabs**. Document this clearly.

## Implementation notes — DT-21/22

**DT-22 embed/viewer mode.** `src/main.ts` reads `readEmbedOptions(location.search)` right after the `App` is created; when `embed=1` it dynamically imports `src/ui/embed/boot.ts` and returns before any editor chrome, input controller, autosave or toast host is built (a 12-line wrapped edit). `bootEmbed` loads the scene (hash payload > `?scene=` > `car`), clears the selection on every change, locks the camera for `camera=fixed`, installs a key forwarder (motor bindings only; nothing else is bound to a key) and, for `interact=1`, the normal `InputController` behind two guards (a left press is dropped unless the simulation is active; double-click is dropped) so grabbing works but drags in edit mode cannot write to the document. `PrefsStore.ephemeral` (tiny edit in `src/app/prefs.ts`) stops the viewer from overwriting the editor's preferences on the shared origin; `persistence.init()` is never called, so no autosave is read or written. The message endpoint is `src/app/embed/bridge.ts` (protocol, strict validation and origin allow-list in the pure `protocol.ts`; documented in `docs/EMBED.md`). The viewer URL builder (`options.ts`) and the iframe snippet (`snippet.ts`) are shared with the Embed dialog (`src/ui/embed/embedDialog.ts`, command `file.embed` in `src/ui/extensions/share-embed.ts`).
Evidence: `e2e/tests/data-embed.mjs` (5 tests: minimal chrome with zero editor elements and working bar buttons; autoplay / controls=0 / camera=fixed / `#s=` payload / unknown scene reported; full postMessage round trip from a host page on another origin (a loopback server on its own port) - ready, getState, play, clock advances, pause, step, reset, setCamera, loadScene, errors for unknown template / command / bad payload; self-posted messages and non-allow-listed origins get no answer, allow-listed origin works; locked editing: selection cleared, mouse drag and Delete / Ctrl+A change nothing, `interact=1` cannot edit while stopped but grabs while running without touching the document) and `data-share.mjs` (Embed dialog: options reflected in the snippet, the live preview viewer honours them, copy button). Pure parts: `tests/embedProtocol.test.ts`.
Gaps: `bg=transparent|dark|light` is not built (opaque sky, no alpha buffer; `docs/LIMITATIONS.md`). Chromium refuses to let an intercepted (`page.route`) document frame a loopback server as a "public to private" request, so the e2e host page is served by a real loopback server instead.

**DT-21 share dialog / QR.** `file.shareDialog` (File menu, next to the unchanged `file.share`) lazily imports `src/ui/share/shareDialog.ts`. The thumbnail (`src/app/share/thumbnail.ts`, own capture because no `renderThumbnail` helper was on this branch: it draws the WebGL canvas into a 2D canvas from a `requestAnimationFrame` callback that runs right after the viewport rendered the frame, since the canvas has no `preserveDrawingBuffer`) shows the scene (e2e counts >6 distinct colours); "copy image + link" writes one `ClipboardItem` with `image/png` + `text/plain`, falls back to the link alone and says which happened (`copyImageAndLink`, unit-tested with fakes for every branch, and e2e reads the real clipboard back and sees both types). Size readout and "N % shorter" come from `ShareResult`. `src/app/share/qr.ts` is a pure byte-mode QR encoder (L / M, versions 1-40, penalty-scored masks, SVG and canvas output). `tests/qr.test.ts` is the evidence: spec constants (format words for L/0 and M/0, version words for v7 and v40, byte capacities v1-10 at L and M, 2953 / 2331 at v40, alignment coordinates, the published "HELLO WORLD" 1-M Reed-Solomon vector) and an independent reader written in the test (own function-pattern map and GF(256) arithmetic: reads both format copies and the version blocks, unmasks, reads the zig-zag, de-interleaves, checks every block's Reed-Solomon syndromes are zero and parses the byte-mode stream) that recovers the input for every version 1-40 at L and M filled to capacity, and for assorted sizes and forced masks. It is not a camera scan of a rendered code (no third-party decoder is in the repo). Links longer than a QR code holds get an explicit message and the scene-file alternative (e2e: 400 random boxes). Open Graph tags: `src/app/share/openGraph.ts`, documented in `docs/EMBED.md` §3 with the host-side workflow.
Coupling note: if another package adds `renderThumbnail` in `src/app/export/`, swap the one call in `shareDialog.ts` (`captureThumbnail`) for it.

Test-run note: the pre-existing e2e "share links: a link from a newer version or a damaged link …" takes ~29.5 s of its 30 s selector budget even on its own (software GL), so it can time out when the machine is busy; it is unrelated to DT-21/22 (passes alone).
