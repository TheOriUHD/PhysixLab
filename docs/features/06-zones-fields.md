# 06 · Zones, triggers, fields, fluids, surfaces, contact physics (package ZN)

Depends on: foundation (components, sensor events, collision groups), ideally CP (actions). Zones are bodies (static/kinematic, sensor colliders) carrying a `zone` component; they render as translucent volumes in edit mode (and optionally while running).

## Trigger / sensor zones
- [x] ZN-1 — Zone component: box/sphere/cylinder/mesh-hull volume, filter (tags, layers, body types), enter/exit/stay events, events delivered to logic/scripts/game layer (`zone` component: def `src/model/components/zone.ts`, runtime `src/physics/components/zone.ts`, vocabulary `src/model/zones.ts`. **Volume** = the body's own shape, the body being a ghost (or having sensor parts): tests/zones.detect.test.ts › 'volumes: any shape is a zone' — a ball passing a sphere at 2.4 / 2.1 m from the centre of a radius-2 zone misses / hits, the cylinder's circular section and height both count, a hexagonal prism (a convex hull) is tested by its own outline, not its bounding box (a box of the same size does catch the corner pass), a compound zone of three sensor parts reports one enter per visit and no stray exit while the ball is in two overlapping parts at once; a rotated box is tested in its own frame, a kinematic zone that moves (and one that turns) reports what it sweeps over. Zones from an imported mesh depend on a mesh-collider shape from the shapes package (LIMITATIONS.md). **Filter**: kinds of body (dynamic / kinematic / both — kinematic bodies are opted in with `ZoneSystem.armSensors`), `Only tags`, `Not tags`, `Only layers`, read from the live body ('the filter reads the live body'); static bodies never enter. **Events**: `enter` / `exit` with the number inside, `stay` every `stayInterval` seconds with the time spent, each switchable; timestamps within 3 steps of the surfaces meeting (the engine reports an overlap one or two steps late — LIMITATIONS.md); a body that starts inside enters on step 1; removed or switched-off bodies exit; live edits keep the bodies inside ('editing the component while bodies are inside…'); snapshots bring the inside sets back and replay bit for bit (tests/zones.detect.test.ts, 23). **Delivery**: protocol-v2 `component` events with `type: 'zone'` and typed payloads (`ZoneEventData`), re-emitted by `SimClient`; the page API `app.zones.on('event')` / `.state` / `.log` / `.feed` (`src/app/zones.ts`) resolves names and is what the HUD, the Zones tab, logic, scripts and the game layer subscribe to (e2e › 'a race in the real worker…' collects the events through it). ## Implementation notes

### Chunk 1 — trigger zones, actions, race timing, world bounds (ZN-1, ZN-2, ZN-3, ZN-34)

**Where things are.** Vocabulary shared by the worker, the page and the tests: `src/model/zones.ts` (the fifteen actions, event names and typed payloads `ZoneEventData`, the published state `ZonesPublic`, time formatting). Component: `src/model/components/zone.ts` (def, one `zone` per body is not enforced: several may sit on one) and `src/physics/components/zone.ts` (runtime). Engine side: `src/physics/zones/system.ts` (`ZoneSystem`, one per world, created by the component host as `host.zones`, reachable as `ctx.zones`), `zones/race.ts` (pure race rules), `zones/actions.ts` (`fire`, `applyField`, spawning), `src/physics/world/bounds.ts` (soft walls and kill / water faces, hooked into `stepping.ts`). Page side: `src/app/zones.ts` (`app.zones`), `zoneCommands.ts`, `zoneSound.ts`, `src/render/zoneViews.ts`, `src/ui/{zonesPanel,zoneHud,zoneTiles,boundsSection,iconsZones}.ts`, `src/ui/extensions/zones.ts` (the Zones tab and the commands), `src/model/zonePresets.ts`, `src/model/content/zn-zones.ts` (prefabs, the *Zones playground* and *Drag strip* scenes). Shared files touched (all marked `-- ZN`): `types.ts` / `factory.ts` / `serialize.ts` (bounds), `physics/components/{host,context,index}.ts`, `physics/world/stepping.ts`, `physics/protocol.ts` (comment), `model/components/index.ts`, `ui/icons.ts`, `ui/libraryPanels.ts`, `ui/worldPanel.ts`, `app/app.ts`, `main.ts`, `styles/app.css` (appended), docs and `tests/{settings,content}.test.ts` (adjusted for the bounds fields and for content files that follow the built-ins).

**Design decisions.**
* *A zone is a ghost body with a `zone` component* (FB-6: zones are not a new entity kind). Detection is the engine's sensor events; the runtime keeps a per-body count of overlapping collider pairs, so compound bodies and compound zones behave. Actions run at the end of the step (`poststep`), never inside the engine's event drain. The zone learns of a body after the engine reports the overlap (one step late): fields act from the second step.
* *One component, one action, several components allowed.* The action list is a closed set (`ZONE_ACTIONS` + `fire`), documented in EXTENDING.md; everything action-specific is `showIf` fields of the one component.
* *Unit = body or group.* `unit: 'group'` makes every body sharing a `parent` group one racer / one thing to lose, respawn, teleport (rigid transform about the body that entered) and launch (impulse shared by mass). This is what "works with any vehicle" rests on, verified with the real car.
* *Everything shared lives in `ZoneSystem` and is saved in snapshots (`@zones`)*, including the race book, respawn points and counts, pending respawns, teleport immunity and spawn bookkeeping; it publishes JSON state only when something changed. Component-level state (the inside sets, cooldowns) is the component's own `saveState`.
* *Bounds extend the existing `bounds` setting without a format bump* (defaults fill in what old files lack); the policy reuses the zone loss machinery so a bounds respawn and a kill-zone respawn behave identically and share checkpoints.
* *Sounds are synthesised* so the app stays a static page; muting is a remembered preference.

**Verification.** 152 new unit tests in 8 files (tests/race, bounds, zones.detect, zones.actions, zones.race, zonePresets, zones.content, zones.model — `.test.ts`) and 8 e2e tests (e2e/tests/zones.mjs); screenshots `zn-add-zones`, `zn-inspector`, `zn-drag-strip-edit`, `zn-race-board`, `zn-zones-tab`, `zn-playground-edit`, `zn-playground-run`, `zn-bounds-section`, `zn-bounds-run` were read. Cost: 600 balls sitting in up to twelve overlapping zones step in ≈ 4 ms against ≈ 2 ms without (mostly the engine's sensor pairs; tests/zones.model.test.ts).

**Known limits** (also in LIMITATIONS.md): discrete sensors (race times ±2 steps, thin gates can be skipped), water edges drown rather than float, soft walls are springs, enable / disable edits the running world only, zones from imported meshes wait for a mesh-collider shape, zone sounds are synthesised presets.

**For the next chunks (ZN-10 …).** Per-body field forces: use `ctx.zones.gravityWinner` / the `applyField` pattern (a zone's `inside` map is the set to act on); a region that needs more than the sensor volume (waves, buoyancy) should read the zone body's pose and `bodyBoundingRadius` like the radial force field does. New zone-like behaviour with its own parameters is a new component, not a new action. `ZoneSystem.moveUnit` / `lose` / `spawnBody` are the safe ways to move, remove and create bodies from a component.
