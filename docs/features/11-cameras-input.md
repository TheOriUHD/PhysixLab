## Implementation notes

### CM-A (cameras and input, minus touch / responsive — see CM-12/13 notes — and CM-20/30/31, which are a later session's)

**Where things live.** `src/app/input/` is the input pipeline: `inputMap.ts` (every command's and held action's bindings, with the user's overrides, conflict detection, presets from `presets.ts`, import / export; the keymap, the shortcut help and tooltips read the *effective* shortcuts through it), `hub.ts` (`app.input`: per frame it turns keyboard + gamepad + touch into the simulation's key set and analog axes), `axes.ts` (dead zone, curve, sensitivity, smoothing, the keyboard ramp), `gamepad.ts` (Gamepad API reader / poller), `profiles.ts` (car, plane, tank, crane, general: which pad input drives which axis name), `capture.ts` (`captureKey`: the single "press a key or pad button" capture used by Settings and by the inspector's key fields), `settings.ts` (persisted in `prefs.input`). `src/app/camera/` is the camera system: `rig.ts` (`app.cameraRig`: mode, projection, lens, shake, transitions, bookmarks), `modes.ts` (the camera-mode registry; `registerCameraMode` also registers `camera.mode.<id>`), `poses.ts` (pure pose maths), `shots.ts` + `shotPlayer.ts` (cinematic shots; `registerShotRecorder` is the recorder hook), `views.ts` (split screen and picture-in-picture), `minimap.ts`, `builtin.ts` (the built-in modes, held actions and commands). UI: `src/ui/input/inputSettings.ts` (Settings dialog), `src/ui/camera/*` (the Camera panel is generated from a section registry: `registerCameraSection`).

**Extending.** A new camera mode is `registerCameraMode({ id, label, icon, order, driven, pose?, enter?, exit? })` from a file in `src/ui/extensions/` (call `registerCameraBuiltins()`-style registration after the built-ins load); a new Camera-panel section is `registerCameraSection`; a held key action (movement, look-behind) is `inputMap.registerAction({ id, label, category, shortcuts, scope })`; a vehicle's gamepad mapping is an entry in `PROFILES` (`profiles.ts`); a video exporter is `registerShotRecorder`. Analog axes are plain names: a joint motor's `axis` field (joint inspector › Motor › Analog axis) and any component text field with `role: 'axis'` read them through `ctx.input.axis(name)`; keys, gamepad sticks / triggers, touch joysticks and the Controls panel's sliders all end up on the same names.

**Decisions worth knowing.**
- *Keys vs axes.* A motor with an `axis` **and** keys: the keys are consumed by the keyboard ramp (they ease the axis up and down like a stick, `Settings › Gamepad & axes › Key ramp`) instead of being sent raw, so a key and a stick never add up to double input; with the ramp setting off the keys go to the simulation as before and the motor clamps `key + axis` to ±1.
- *Pad buttons are keys.* A pad button produces the key code `Pad<Button>` (`PadSouth`, `PadRT` …) plus, for the D-pad and shoulder buttons, the arrow / Q / E codes (`PAD_TO_KEY`), so every scene that binds keys also plays with a pad; the inspector's key fields accept a pad button press as a binding.
- *Bookmarks recall with `Shift+1…9`, save with `Ctrl+Shift+1…9`* (plain digits add shapes, `Ctrl+digit` belongs to the browser); the camera cycles with `Z`, and every mode has a command (`camera.mode.<id>`) in the palette. The checklist's "(Ctrl+1..9 / 1..9 recall)" is therefore deliberately different.
- *Orthographic = the same camera object.* `DualCamera` (a `PerspectiveCamera` subclass) switches its projection, and answers `isPerspectiveCamera` / `isOrthographicCamera` accordingly, so the renderer passes, picking, the orbit controls, the view cube, labels and overlays need no changes.
- *Split screen = DOM.* The main view keeps its canvas and shrinks to its pane's rectangle; the other panes are 2D canvases filled from off-screen renders of the same scene (so picking, the gizmo and the orbit controls keep working in the main pane unchanged).
- *Scene data.* Bookmarks, shots, the split layout, picture-in-picture windows and the minimap are `SceneDocument.cameras` (optional; sanitised in `src/model/sanitize/cameras.ts`; edits go through `store.setCameras`, which is undoable and notifies with the `meta` event). Lens, speeds and the motion preference are per browser (`physicslab:camera:v1`).

**Verification.** `tests/input.test.ts`, `tests/camera.test.ts`, `tests/shots.test.ts` (pure logic, the real engine for analog motors), `e2e/tests/cm-input.mjs`, `e2e/tests/cm-camera.mjs` (real UI in headless Chromium; the gamepad is a stubbed `navigator.getGamepads`). Known honest limits are in `docs/LIMITATIONS.md › Cameras and input (CM-A)`.

### CM-12/13 notes

**Touch (CM-12).** `src/app/touch/` holds the logic that can run in Node (`gestures.ts` finger set, two-finger classifier, long-press state machine, pan / pinch / snap maths; `joystick.ts` stick vector and pad writes; `settings.ts` the sanitised `InputSettings.touch` block) and `touchController.ts` (DOM: capture-phase pointer listeners on the canvas). `src/ui/touch/overlay.ts` draws the joysticks and buttons into `app.shell.stage`; they write into `app.input.touch` (a gamepad-shaped `PadState`) and set `touchActive`, so the active vehicle profile maps the sticks exactly like a pad and buttons become `Pad<Button>` codes plus the `PAD_TO_KEY` keys. Each control owns its pointer (pointer capture), so both sticks and any buttons work at once; release, cancel, hiding, blur and tab-hide all reset the pad.
- *Camera mapping.* One finger = the active tool (select, marquee, drag-move, gizmo). Two fingers = OrbitControls' `DOLLY_ROTATE` (pinch zooms, drag orbits) or `DOLLY_PAN` (Settings › Touch › Two-finger drag); one-finger orbit is switched off (`touches.ONE = null`) because it used to fight the selection. Three fingers = pan, done in `touchController.ts` (OrbitControls has no three-pointer mode). A second finger puts `InputController.cancelGesture()` to work: the marquee disappears, a drag-move is undone without leaving an undo step, a physics grab is released. While the transform gizmo is being dragged, extra fingers are swallowed so they cannot corrupt that drag.
- *Long press* (default 500 ms, ≤ 10 px of drift, Settings › Touch › Long-press time) opens the viewport context menu and cancels the one-finger gesture, so releasing does not deselect and moving afterwards does not drag. It fires from an animation frame so a lift that is already queued (a long frame) wins. It does not fire while a physics grab or a gizmo handle is held; a long press on the *centre handle of the gizmo of a selected object* therefore belongs to the gizmo (press beside the handle instead).
- *Two-finger drag to move the selection* is a **mode** (Settings › Touch › Move selection with two fingers, default off) because orbit and move would both claim the gesture: with the mode on, in edit mode with something movable selected, a two-finger drag moves the selection on the ground plane (one undo step, grid snap honoured) and a pinch still zooms (decided by the first 10 px of travel, then locked for that gesture); with nothing selected the two fingers orbit again. Judged once per frame so the fingers' interleaved events do not read as a pinch.
- *Visibility.* `touchControls: auto` = `(pointer: coarse)` or `maxTouchPoints > 0`, and the overlay is shown while a simulation is active (the controls do nothing in edit mode); `on` always shows it, `off` hides it. The Touch tab chooses joysticks (both / left / right / none), the buttons (LT LB Reset ↑ ↓ ← → RT RB A B X Y Play), size, opacity and a left-handed mirror; `view.touchControls` toggles it from the palette / View menu. While the overlay is up the hint bar and tool options move to the top and the selection bar is hidden (the bottom corners are the controls').
- *Hit areas.* Overlay buttons are ≥ 44 px (`max(44px, 54px × size)`), `(pointer: coarse)` raises icon buttons, tabs, menu items to 44 px, the gizmo is 1.2× larger on touch devices and path control points are picked within 26 px (12 px for a mouse). `touch-action: none` was already on the canvas.

**Mobile layout (CM-13).** Below 900 px (`NARROW_QUERY`) the three docked regions become a left drawer (library), a right drawer (inspector / outliner / world …) and a bottom sheet (telemetry dock); `src/styles/cm-mobile.css` does the geometry in media queries, `src/ui/mobile/layout.ts` drives it through the existing `showLeft / showRight / showBottom` preferences (so every command and the dock manager still work; at most one sheet is open; opening one closes the others). A bottom navigation (Library · Inspector · Data · Tools · View · Menu) opens them, a scrim / close button / Escape closes them. Tools and View open the floating toolbox and view bar as popovers (tapping the viewport dismisses them); Menu is the combined File / Edit / View / Help menu plus the palette. The top bar keeps the logo, play / step / stop and undo / redo; everything else is in the navigation or the Menu. The desktop panel arrangement is stashed in `localStorage` (`physicslab:desktop-panels`) while narrow and restored when the window is wide again. Safe-area insets and `viewport-fit=cover` are in place; landscape phones (≤ 520 px high) get an icon-only navigation. The old `max-width: 860px` "hide the library" rule in `app.css` was removed (superseded). Wide layouts are untouched: everything is inside media queries, and `cm-mobile.mjs` asserts the docked columns at 1600×900 and 1280×720.

**Verification.** `tests/touch.test.ts`; `e2e/tests/cm-touch.mjs` and `e2e/tests/cm-mobile.mjs` (real touch emulation, screenshots read at 390×844, 820×1180, 1280×720, 1600×900). Software-GL frames take about a second, so those tests set a 9 s long-press time for taps and wait on page-side conditions rather than fixed delays.

**Not done / for others.** Floating windows of the dock manager (`dock-float-layer`) are not adapted to phones (they stay desktop-style); the Keyboard and Gamepad tabs of Settings were not re-flowed for 390 px (the Touch tab is). The telemetry panels' own layouts were not changed.
